# CORE-INTEGRITY-002 evidence — the two surviving pre-CAS collision runs

**Exported 2026-07-26 at `67e80120`, immediately before both runs were dropped
from the local MongoDB.** They were dropped because their colliding
`order_index` values prevented `uq_run_order_index` (`core/db.py:43`,
`unique=True`) from ever building, which failed 16 DB-layer tests at setup.

**Why this export exists.** These two runs held the *only surviving instances*
of the `order_index` collision class. `c2d7b4c6` (2026-07-25 12:43:10 UTC) added
the intervention `next_order_index` CAS, and **zero collisions have occurred
since** — so the class cannot be regenerated by running the engine today.
Deleting the runs without exporting would have destroyed the only material
`memory/CORE-INTEGRITY-002-CONCURRENCY-CAS.md` could ever be investigated from.

**This is evidence, not canonical state.** Nothing here is a frozen baseline,
nothing replays into a current run, and no test reads it. Neither run used the
harness seed `living-agents-stage6`; both are ad-hoc API runs with random seeds,
left `status: "running"`.

---

## What it reproduces

A **violation of the per-run global monotonic `order_index` sequence**: two
distinct accepted events in one run sharing a single `order_index`. Per
`core/db.py`'s own comment, "no two accepted events in the same run may ever
share one." Nothing enforced that at the storage layer before `c2d7b4c6` — the
pre-existing `ix_run_event_boundary` index is non-unique and query-only — so a
racy writer computing `next_order_index` without CAS (the intervention endpoint,
`api/routes.py`) could interleave a colliding value into the canonical sequence.

**13 colliding `order_index` values, 26 events**, and the two runs show
*different shapes* — which is the most useful thing here:

| Run | Scenario / seed | Colliding `order_index` | Shape | Created (UTC) |
|---|---|---|---|---|
| `run-1fb2793e6a64` | `living_settlement` / `ba1107a363` | `177` | **isolated** — one collision, ticks 8 and 9 | 2026-07-19 16:53–16:54 |
| `run-9bc94ad9a5e8` | `basic_survival` / `24088d13e3` | `13454`–`13465` | **contiguous run of 12** | 2026-07-22 05:46–06:30 |

The contiguous block is the stronger lead: twelve consecutive indexes colliding
looks like one sustained racing episode re-issuing the same counter window, not
twelve independent incidents. `run-1fb2793e6a64`'s single collision spans two
*different ticks* (8 and 9) and two different frames — one of them
`run-1fb2793e6a64-ext-infl-ec4dc57dd9`, an **external-influence frame**, which is
the intervention path the CAS was added to guard. That is a direct, and
unexamined, corroboration of the suspected mechanism.

## Contents

Canonical MongoDB Extended JSON (`bson.json_util`), one document per line,
sorted by `_id`, so re-exporting the same data is byte-reproducible. Plain
`.jsonl` rather than gzip, deliberately: `grep` and `jq` must work directly on
it or the stub is no more investigable than before.

```
run-<id>/kernel_runs.jsonl           the run record
run-<id>/accepted_events.jsonl       full event history
run-<id>/commit_frames.jsonl         frame records
run-<id>/entities.jsonl              final entity state
run-<id>/rejected_proposals.jsonl    rejections
run-<id>/activation_diagnostics.jsonl
run-<id>/external_influences.jsonl   the intervention path under suspicion
run-<id>/COLLISIONS.json             the colliding order_index values, extracted
MANIFEST.json                        per-file document counts, byte sizes, sha256
```

Every `.jsonl` line was validated to round-trip through `json_util.loads` at
export time. Verify integrity against `MANIFEST.json`:

```python
import hashlib, json, pathlib
m = json.loads(pathlib.Path("memory/evidence/core-integrity-002/MANIFEST.json").read_text())
for path, meta in m["files"].items():
    actual = hashlib.sha256(pathlib.Path(path).read_bytes()).hexdigest()
    assert actual == meta["sha256"], path
```

Load a run:

```python
from bson import json_util
events = [json_util.loads(l) for l in open(
    "memory/evidence/core-integrity-002/run-9bc94ad9a5e8/accepted_events.jsonl",
    encoding="utf-8")]
```

Restoring into a scratch database is `insert_many` on the parsed documents —
but **do not restore into `simulation_sandbox`**: it would re-break
`uq_run_order_index`, which is the whole reason these were dropped.

## What it can and cannot answer

**Can:** whether the collisions correlate with external-influence /
intervention frames; whether the contiguous block shares a frame, a tick, or a
wall-clock window; whether colliding events were otherwise valid; what the
`head_revision` sequence looked like across the racing window; whether
`commit_frames` shows overlapping frame identities.

**Cannot:** confirm the fix. These predate `c2d7b4c6` entirely, so they say
nothing about whether the CAS is *sufficient* — only what the defect looked like
without it. Confirming sufficiency needs the canary probe named in
CORE-INTEGRITY-002's "Next actions", which remains unwritten.

**Open, unrelated question also recorded here** because it surfaced in the same
audit: the 64 same-tick `energy` collisions measured in `collective_groups` are
a *different* phenomenon (same tick, same entity, same field — not an
`order_index` violation) and remain **UNKNOWN**. See
`memory/REGISTRY-COMPONENT-OWNERSHIP.md`. Do not conflate the two.
